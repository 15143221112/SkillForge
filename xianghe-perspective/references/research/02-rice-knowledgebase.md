## 一、心智模型候选（10 个）

### M1. 先立骨架：总纲 → 分层 → 明细，不直接堆内容
- **一句话**：垂直知识库先定「层」和「边界」，再逐层填充内容，保证可扩展可维护。
- **证据**：
  - 《全流程建设总手册》把建设拆成 **S0–S9 九阶段**（目标架构→来源采集→MinerU解析→知识整理→入库→检索路由→回答范式→对话记忆→数据报告→评测迭代），并明确「你现在的位置：已在做 S1+S2」。
  - 《建设总纲》双轴分类模型：「产业链轴(产前/产中/产后) × 生育周期轴」+ 生产要素交叉 + 知识类型标签，「每个知识块入库时至少挂主轴A+副轴B+生产要素+知识类型+主体」。
  - 《大纲》按「11分支 → 阶段 → 环节 → 知识点」四级展开，知识点为最小入库单元。
- **出现文档**：全流程建设总手册、建设总纲、大纲。

### M2. 术语零容忍：专业术语是生命线，要固化、要校对
- **一句话**：农业术语错一个，结论就错；宁可慢，不能错，且要用工程手段把术语「焊死」。
- **证据**：
  - 已提炼思维文档：语音转写把「施穗肥会不会造成贪青晚熟」错译成「碎肥/贪心晚熟/贪清碗苏/麒麟省/分孽肥」，用户强烈纠正，要求大模型校正标点、纠专业术语。
  - 《混合检索开发文档》专建 **jieba 领域词典 userdict.txt（156 词）**：「把品种名、地名、农业术语设为固定词，防止被 jieba 默认词典拆散（如默认会把'绥粳109'拆成'绥粳+109'）」；并列出踩坑：词典里写 `#` 注释会导致整词典加载失败、专有名词全被拆散。
  - 检索质量闸门②「专有词硬过滤」：对含数字/字母的高置信专有词（绥粳109、QX/T 182）做硬命中校验。
- **出现文档**：混合检索开发文档、RAG技术栈路线、已提炼思维文档。

### M3. 模型分工，各司其职（按能力 vs 显存资源配任务）
- **一句话**：不用一个模型干所有事；长文本问答、图片OCR、向量、精排分给专职模型，显存（32G）按「能力 vs 资源」分配。
- **证据**：
  - 《WeKnora开发文档》实测显存账本：「embedding 10.7G + rerank 2.4G + VL 11.4G = 已用 ~24.5G，剩 ~7.5G」，并警告「再起大模型会紧张」。
  - 分工矩阵：问答→qwen-plus（大 context）；图片解析→Qwen2.5-VL-7B（端口8002，max-model-len 8192）；向量→Qwen3-Embedding-4B（2560维）；精排→bge-reranker-v2-m3。
  - 《信息录入说明》根因澄清：长文本走 `messages[].content`（完整透传），而 model params 逗号拼接会截断 message——即「传参方式也要按模型/链路分工设计」。
- **出现文档**：WeKnora开发文档、导入报告、信息录入LLM提取说明。

### M4. 数据治理先行：导入前定 schema/分类/去重，导入结果可审计
- **一句话**：大量资料入库前先定规则，不裸导；每一步留痕，成功/失败数和失败原因可查。
- **证据**：
  - 《WeKnora导入报告》：导入前对 596 个文件做完整性校验（无0字节、md全UTF-8可解码、PDF文件头 `%PDF`、图片文件头 JPG `FFD8FF`/PNG `89504E47`）；重名文件（11个目录下的 `回答范式.md`）「带目录前缀改名区分，全部保留无丢失」。
  - 结果可审计：「594 成功(99.7%) / 2 失败(0.3%)」，两个失败文件单独列出原因（WeKnora 摘要 context 限 1024 超限），并附 `weknora_upload_log.csv`（596 行逐文件状态）。
  - 《导入规则方案》：标准知识块模板固定【类别】【维度】【主体】【子主题】【图片】+ 正文 + 来源URL；chunk_size 300~500、overlap 50。
- **出现文档**：WeKnora导入报告、导入规则分类体系方案。

### M5. 多维度回答：不只给答案，给「分析结构 + 固定章节」
- **一句话**：对「某品种怎么样/会不会贪青」这类问题，按维度模板（子查询集 + 章节schema）组织答案，缺维度诚实标注。
- **证据**：
  - 《多维度回答架构方案》五层：意图解析→模板选择→检索编排→答案生成→多轮切换；章节schema强制 LLM 按「品种概述/生育管理/水肥/病虫害/生理胁迫/收获米质」固定章节作答。
  - 《Skill全景体系》穷尽出 **11域/49个 Skill**，每个 Skill = 触发词(description) + 一种回答范式；并归纳「豆包回答水稻只有7种组织范式」（实体/流程/诊断/对比/推荐/概念/数据）。
  - 母题扩散文档实例：Q1-1 把「积温差50℃能否试种」拆成 5 项指标层级核验（积温总量→安全齐穗期→孕穗低温→抽穗扬花→灌浆日照），最后给「两条硬杠任一不满足不建议试种」。
- **出现文档**：多维度回答架构/选型、Skill全景体系、五优稻4号母题扩散。

### M6. 诚实拒答：「没有就说没有」，不硬凑不相关
- **一句话**：知识库边界内答，边界外拒答；拒答本身是质量护栏，不是失败。
- **证据**：
  - 《混合检索开发文档》主题白名单：「广东种水稻/小麦积温」会被向量+重排以 0.85~0.99 高分误召回东北条目，故前置 `isOutOfScope` 直接返回空，不进检索。
  - 质量闸门三件套：重排阈值 0.5 剔除 + 专有词硬过滤 + 证据充分性拒答（过滤后为空→返回空并记录拒答查询，供回补知识库）。
  - 多维度生成铁律：「某维度检索无内容，明确写'知识库暂无该维度资料'，禁止编造」。
- **出现文档**：混合检索开发文档、RAG技术栈路线、多维度回答架构方案。

### M7. 先算后生成：LLM 只组织文字，不碰算术（防幻觉）
- **一句话**：数值、进度、预警全由规则/SQL 算好，LLM 负责把「数据结论+知识依据」组织成报告。
- **证据**：
  - 《导入规则方案·数据驱动报告》流水线：三温算活动积温→田块定品种→农事比对→知识库给阈值→**LLM 出报告**；明确「LLM只做组织不做算术——数值、进度、预警全由规则/SQL算好，LLM负责生成报告文字，避免幻觉」。
  - 报告内容模板：「实测积温 X℃ vs 品种需 Y℃ → 进度超前/正常/滞后」「孕穗期日均<19℃预警」——阈值都是规则。
- **出现文档**：导入规则分类体系方案、全流程建设总手册 S8。

### M8. 复用不造轮子：先对标业界主流范式，拒绝过度设计
- **一句话**：先判断「已知结构 vs 发现关系」，能用 metadata/注册表表达的绝不上图谱；直接对标 Dify/LangChain/Mem0/WeKnora。
- **证据**：
  - 《多维度回答_主流方案选型》明确否决 GraphRAG：「实体覆盖率不足70%时 KG-GraphRAG 大概率不如纯向量 RAG；你的维度结构是预定义好的，不需要靠图去发现实体关系」「对你的场景是过度设计」。
  - 给出业界标准组合：「Router(意图路由) + Agentic RAG(检索即工具) + Skill/工具注册表」，并点名「最值得对标 Dify」。
  - 《对话记忆方案》：「不一定引入框架，自研同样的三层机制即可，参考 Mem0 的 add/search/update/delete」。
- **出现文档**：多维度回答_主流方案选型、对话记忆方案、WeKnora开发文档。

### M9. 渐进式落地：MVP 先跑通，按 P0/P1/P2 分批，不一次全做
- **一句话**：先跑通最小闭环（单轮多维度），再叠加多轮切换/管理页；每个方案都给「先做哪几步」。
- **证据**：
  - 《BladeX开发实施方案》落地步骤 P1 数据层→P2 路由→P3 检索+生成(MVP单轮)→P4 多轮→P5 管理页，「建议先做 P1~P3」。
  - 《Skill全景体系》落地优先级：P0 必做（品种档案/时间线/水肥/病虫害/冷害/综合诊断/全景报告7个）、P1 高价值、P2 长尾补充，「别一次全做」。
  - 《智能体编排方案》建议：「先用方案2（5个独立流程）跑通业务，再做方案1（父流程聚合）」，因为父流程 DSL 节点数是5倍、调试成本高。
- **出现文档**：BladeX开发实施方案、Skill全景体系、智能体工作流编排方案。

### M10. 内容资产化：把「怎么做」沉淀成可复用资产，持续扩容
- **一句话**：每种能力落成可复用文档/题库/Skill；高频问题本身是资产，持续扩容（500→900→1300）。
- **证据**：
  - 问答数据集：《高频问题清单500条》→《扩容501-900》→《扩容901-1300》→《1300条合并版》，且合并时带「240条临界题三模型裁决（共识/最优源/证据等级/三模型答案对照）」。
  - 修复记录文档自我约定：「每次修复后同步更新本文档……涉及源码改动必须同时给出修改前/修改后代码块」。
  - 《母题扩散》把单品种分析复盘成「可复用内核」：四段式（主要事项/易出问题/补救措施/指导意见）直接作为入库格式规范。
- **出现文档**：1300条合并版、高频问题清单系列、修复记录文档、五优稻4号_分析维度复盘。

## 二、决策启发式候选（13 条，「如果 X，则 Y」+ 案例）

1. **如果用户历史问答是「登录人id全量塞给LLM解析」→ 必然 token 爆炸，改三层记忆。**
   - 案例：《对话记忆方案》判定「轮数多了必炸，且是必然」；根因是「把历史当必须全量喂的东西，而非可按需检索的东西」。升级为 Redis 最近N轮 + 摘要压缩 + rag_user_memory 向量检索。

2. **如果纯向量检索召不到专有名词（品种名/地名/公式）→ 加 BM25 关键字路 + jieba 领域词典双路召回。**
   - 案例：纯向量约 78 分，加混合检索后 Recall@5 到 98%；「绥粳109/通禾899/辉南县」向量模型不认识。

3. **如果 query 含括号/英文导致召回为空（「度日（Degree-Day）」）→ 召回前 normalizeQuery 剥离括号与英文，但重排仍用原始 query 保语义。**
   - 案例：规范化只作用召回层，重排走 `cleanRerankQuery`；规范化结果为空（纯英文）时回退原始 query。

4. **如果跨地域/跨作物问题被高分误召回（广东种水稻 0.85 分）→ 主题白名单前置拒答，根本不进检索。**
   - 案例：重排只判语义相关、不理解「广东≠黑龙江、小麦≠水稻」，故用 `blade_dict_biz` 业务字典表维护越界词，后台改词即热生效、无需重启。

5. **如果 LLM 字段提取不稳定/输出空对象 → 先怀疑传参管道（逗号截断 vs content透传），不要先怪模型和提示词。**
   - 案例（最强证据）：《信息录入说明》先认定「deepseek 提取不稳定」，改了5轮提示词/降温度/加强示例均无效；最后节点级透传发现根因是 **model params 逗号拼接把 message 截断到第一个逗号前**，改走 `messages[].content` 透传后三条用例全部成功。原文：「模型和提示词一直是好的」「问题集中在 deepseek」的结论是错的。

6. **如果源变量为 null（如 index 本次未生成）→ 跳过注入，绝不向 ConcurrentHashMap 写 null。**
   - 案例：`setParameter("index", null)` 触发 NPE；修复为 `if (value == null) continue;`。

7. **如果要兼容子流程内多种变量引用方式 → 同一值按「裸 type / start id 前缀 / start name 前缀」三种形式同时写 variables。**
   - 案例：子流程内 llm 用 `${开始.message}`、http 用 `node_<startId>.bladeAuth`、code 用 `node_<httpId>.body`，引用方式不统一导致全 null，多形式注入后消除 NPE。

8. **如果要做设备/闸门操作 → 后端只把口述解析成 JSON + 返回路由，绝不执行；由前端弹确认后 MQTT 下发。**
   - 案例：闸门子流程 `needConfirm=true`，后端返回 `{deviceId,action,value}`，前端逐个调 `POST .../mqtt/property/set`；设计原则写死「后端绝不执行设备操作」。

9. **如果图片要进知识库 → 不专门做软件，写几十行 Python 脚本（image2minio），上传后把 md 里图片引用替换成 MinIO URL。**
   - 案例：「前期一个脚本足够，不用先做软件」；桶设公开只读，URL 永久可访问。

10. **如果要扩展新回答维度 → 新增一条 rag_skill 记录 + 一条维度模板记录，核心代码零改动。**
    - 案例：「新增维度 = 新增一个 Skill/工具 + 在注册表登记」，靠 description 渐进式披露（只暴露一行描述，命中才加载 SKILL.md 全文，省 token）。

11. **如果 query 宽泛（「五优稻4号怎么样」）→ 3~5 路子查询并行召回 + RRF 合并；如果 query 具体（「那它的病虫害呢」）→ 单维深检索。**
    - 案例：breadth=broad 走多路、narrow 走单路；「子查询别太多，3~5路最佳，过多引入噪声」。

12. **如果模型 context 不够导致个别文件导入失败（WeKnora 摘要限 1024）→ 拆分重传或忽略 <0.3% 边缘样本，不为它改整体流程。**
    - 案例：2 个失败文件（7.5KB md + 2.34MB PDF）「影响极小（不到0.3%），可后续拆分重传或忽略」。

13. **如果要给一个技术选型拍板 → 先问「是已知结构，还是需要发现关系」；已知结构用 metadata 标签，不上 GraphRAG。**
    - 案例：他的品种/维度/子主题是预定义已知结构，用结构化 metadata 标签「比建图便宜得多」，故否决 GraphRAG、选 Skill 注册表。

## 三、表达 DNA 观察（他在水稻项目中怎么沟通）

### 3.1 结论先行 + 一句话总结
- 每个方案文档开头先给结论：「**结论先行：框架完全支持你要的5类场景，之前'不好使'是DSL结构细节问题，不是框架做不到**」（智能体编排方案）。
- 几乎每份方案结尾都有「**一句话总结**」，把整份架构压成一行（多维度回答、对话记忆、导入规则、RAG路线均如此）。

### 3.2 表格密集，决策可视
- 对比表是他的默认表达：方案选型表（原生PgVector HYBRID ❌ vs 应用层BM25 ✅）、7种范式表、11域49 Skill表、端口/服务清单表、显存账本表。他倾向于把选项、参数、坑全部表格化，让人一眼拍板。

### 3.3 明确列出「需要你确认的决策点」
- 《智能体编排方案》结尾直接抛 5~6 个待拍板项（流程拆分方案同意吗？路由表写死还是查库？定时任务用 blade_job_info 还是 crontab？），并附「我这次是先规划、你确认、再生成，每个 DSL 都会对照源码校验逻辑自检」。——他把「决策权」显式交回，不替用户闷头决定。

### 3.4 源码实证，拒绝编造
- 反复声明「**所有结论均来自真实源码/库数据，未编造**」（整体逻辑分析）；测试报告每条用例都附真实 HTTP 状态、真实报错原文（如 `queryEmb is null`、`Object.hashCode() key is null`）。
- 排错时给「铁证」：抓 LLM 节点 `llmParams.messages[1].content` 逐字为 13 个字符的 `${开始.message}`（未插值），用字节级证据定位问题，而非主观猜测。

### 3.5 修改前 / 修改后代码块对照
- 《修复记录文档》硬约定：「涉及源码改动必须同时给出修改前/修改后代码块」，并附问题现象→根因→修改文件→效果的完整链条。他把「改了什么、为什么改」当成必须留痕的产物。

### 3.6 术语纠正：错译即红线
- 语音转写把「施穗肥会不会造成贪青晚熟」错成「碎肥/贪心晚熟」时，他要求用大模型校正标点、纠专业术语，不能直接入库。术语（穗肥、贪青晚熟、分蘖、公顷/公斤、亩）逐词核对是他的沟通红线。

### 3.7 对回答结构的要求：有结论、分维度、标边界
- 知识库回答模板（见1300数据集）固定为：**结论（先给判断）→ 依据/操作要点（分条）→ 边界兜底（"补贴、收购价等以当地当年官方通知为准"）**。
- 临界问题不给绝对答案，给「正常/极端」两种情形：如 Q1-1「两条硬杠任一不满足不建议试种；都满足也只是'可试'，需配套……且第一年小面积≤5亩验证」。

### 3.8 向组织者分级报障
- 测试报告把问题分级上报：「【致命/主流程】」「【阻塞A】RAG embedding 未配置」「【阻塞B】HTTP节点鉴权未通」，并给「修完全局可通」的优先级建议。他不堆问题，而是按影响面排序、给修复顺序。

## 五、矛盾与张力（3 对）

### 张力 1：追求完美全面 ↔ 快速迭代可用
- 一面：穷尽 11 域/49 Skill、11 分支、7 范式、1300 问答、S0–S9 全周期，追求「覆盖东北水稻 80%~90% 高频问题」。
- 另一面：MVP 先跑通单轮多维度，P0 只起手 7 个 Skill；2 个导入失败文件（0.3%）直接忽略；图片用几十行脚本而不是做软件。
- **张力本质**：他知道终态要全，但坚决不为全量牺牲当下可跑通——「先做哪几阶段」永远排在「能不能一次做全」前面。

### 张力 2：自研发可控 ↔ 复用开源平台
- 一面：记忆、检索、Skill 都强调「自研同样的机制即可，不必引入框架」，喜欢亲手搭三层记忆、BM25、RRF。
- 另一面：整体运行时直接用 WeKnora（「手册变供料方，WeKnora 当运行时引擎」），并主动对标 Dify/LangChain/Mem0。
- **张力本质**：在「机制理解与可控」上自研（吃透原理），在「重型运行时」上复用（不重复造引擎）。

### 张力 3：术语/精确零容忍 ↔ LLM 天然不稳定
- 一面：术语零容忍、专有词硬过滤、缺失维度诚实标注，近乎苛刻。
- 另一面：他最终接受 LLM 抽取精度只能「提示词迭代 + 拒答兜底」，不追求消灭幻觉（测试报告把残留 LLM 抽取偏差归为"不阻塞验收的提示词优化项"）。
- **张力本质**：他不对抗 LLM 的概率本质，而是用「护栏（拒答/阈值/白名单/规则算算术）」把不稳定关进笼子。

## 六、关键决策案例（6 个，背景→考虑→选择→结果）

### 案例 1：模型分工与显存分配
- **背景**：服务器 RTX 5090 32G，要同时跑 embedding、rerank、多模态 VL，还要问答。
- **考虑**：按「能力 vs 资源」分配——长文本问答用大 context 的 qwen-plus；图片专职 VL；向量/精排各占一份显存。
- **选择**：embedding(Qwen3-Embedding-4B, 8080) + rerank(bge-reranker-v2-m3, 8001) + VL(Qwen2.5-VL-7B-AWQ, 8002) 分端口部署。
- **结果**：实测占用 24.5G、余 7.5G，并写下「再起大模型会紧张」的显存账本作为后续约束。

### 案例 2：信息录取值提取的「根因反转」（最能体现他的排障思维）
- **背景**：LLM 从用户消息提取表单字段时，设备注册/意见反馈输出空对象，农事记录却正常。
- **考虑**：先按常规认定「deepseek 对属性值提取不稳定」，改了 5 轮提示词、降温度 0.7→0.1、加强示例、加 code 预处理字段定义——均无效。
- **选择**：拒绝继续调提示词，做节点级透传逐层排查，发现根因是 **model params 逗号拼接把 message 截断**（只取到第一个逗号"登记一台新设备"），而非模型/提示词。
- **结果**：改走 `messages[].content` 完整透传后，三条用例全部正确提取；并留下铁律「先怀疑传参管道，不先怪模型」。文档中明确更正「此前结论是错的」。

### 案例 3：多维度回答架构——否决 GraphRAG，选 Router+Skill 注册表
- **背景**：要让知识库像豆包一样按维度组织答案、追问时能切维度。
- **考虑**：候选技术有 CoT、图数据库/GraphRAG、Skill。他查业界实测：实体覆盖率<70% 时 GraphRAG 不如纯向量 RAG；而他的维度是预定义已知结构，不需要图去发现关系。
- **选择**：不上 GraphRAG；采用「意图路由(Router) + Agentic RAG + Skill/工具注册表」，chunk 打 metadata 维度标签，新增维度=新增一条注册记录。
- **结果**：明确「在现有混合检索之上加编排层，不推翻任何已完成代码」；对标 Dify/LangChain 落地。

### 案例 4：闸门操作的安全边界设计
- **背景**：用户语音说「打开3号田闸门开度50」，系统要执行设备动作。
- **考虑**：直接后端执行风险高（误操作不可逆）；但完全不接设备又不闭环。
- **选择**：后端只把口述解析成结构化 JSON `{deviceId,action,value}` + 返回路由，`needConfirm=true`；绝不执行，由前端弹确认框、用户确认后逐个调 MQTT 下发。
- **结果**：单开/多开/按田块批量/open/close/set 全部测通，且操作控制权牢牢留在前端确认环节。

### 案例 5：596 文件批量导入的治理策略
- **背景**：596 个文件（471 md + 15 PDF + 110 图片）要入 WeKnora。
- **考虑**：怕裸导出乱码/坏文件/重名覆盖；要让导入可审计。
- **选择**：导入前先本地校验（0字节/UTF-8/PDF文件头/图片文件头）；11 个重名 `回答范式.md` 带目录前缀改名；REST API 批量上传 + 逐文件写 csv 日志。
- **结果**：594 成功(99.7%)/2 失败(0.3%)，失败原因逐条记录；图片 110 张全部多模态解析成功。

### 案例 6：对话记忆从「全量塞」改「三层检索」
- **背景**：现状是「登录人id 从问答表取全部历史 → 全量塞给 LLM 解析」。
- **考虑**：轮数一多必然 token 超限、无关历史污染判断、成本飙升、变慢；根因是「把历史当必须全量喂的文本，而非可按需检索的知识」。
- **选择**：改三层——Redis 最近N轮 + 早期轮次摘要压缩 + rag_user_memory 向量检索；知识库(领域)与记忆(用户)分开存、分开取、一起注入。
- **结果**：「轮数再多也不会爆」；并复用同一套向量检索基建，把田块画像/种植进度做成结构化长期记忆。
